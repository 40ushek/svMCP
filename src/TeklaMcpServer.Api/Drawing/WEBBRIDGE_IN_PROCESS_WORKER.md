# WebBridge in-process worker

## Идея

Использовать `WebBridge`, загруженный внутри Tekla, как быстрый worker для тяжёлых операций Tekla Open API.

Внешний MCP-сервер остаётся основным интерфейсом. Для тяжёлых вызовов он может передавать команду локальному worker внутри Tekla, минуя отдельный `TeklaBridge.exe` и повторное IPC между каждой операцией.

```text
MCP Server (.NET 8)
        |
        | защищённый named pipe или localhost IPC
        v
WebBridge внутри Tekla (.NET Framework 4.8)
        |
        | последовательная очередь Tekla-вызовов
        v
Tekla Open API
```

## Что уже есть

- `WebBridge` использует `Tekla.Structures.WebBrowser` и Fusion и работает как расширение Tekla.
- `TeklaModelAssistant.McpTools.dll` загружается WebBridge как зависимость.
- `AgenticIntegrator` находит публичные методы инструментов через reflection и вызывает их напрямую.
- Инструменты уже создают `Model` и `DrawingHandler` без внешнего `TeklaBridge`.

Это подтверждает техническую возможность in-process режима, но ещё не доказывает выигрыш по времени.

## Ограничения

- Поток, принимающий внешние команды, не должен напрямую вызывать Tekla API.
- Все вызовы Tekla должны проходить через один сериализованный Tekla-контекст или очередь.
- `STA` сам по себе не является способом ускорения и не заменяет правильную передачу вызова в контекст Tekla.
- MCP через `stdin/stdout` внутри Tekla не нужен; для внешнего MCP предпочтителен локальный named pipe.
- `TeklaMcpServer` нельзя просто загрузить в WebBridge: он рассчитан на .NET 8, тогда как WebBridge и Tekla API работают на .NET Framework 4.8.

## Безопасность локального канала

Если worker принимает команды извне, канал должен:

- быть доступен только текущему пользователю;
- не слушать внешний сетевой интерфейс;
- принимать только белый список команд;
- проверять токен или другой идентификатор клиента;
- работать только пока активен WebBridge;
- журналировать команды и ошибки.

## Предлагаемый первый эксперимент

Не переносить весь сервер. Добавить один экспериментальный вызов для `get_all_parts_geometry_in_view`:

1. принять команду в WebBridge;
2. поставить её в единственную очередь Tekla-вызовов;
3. выполнить чтение геометрии внутри Tekla;
4. вернуть компактный JSON-результат;
5. сравнить время с внешним `TeklaBridge` на том же виде.

Измерять отдельно:

- время вызова Tekla API;
- время сериализации;
- время передачи результата;
- полное время MCP-вызова.

Только после замера решать, какие команды переносить в in-process worker.

## Не является целью

- запускать весь MCP-сервер внутри Tekla;
- заменять внешний `TeklaBridge` сразу;
- добавлять общий сетевой HTTP-сервис;
- распараллеливать вызовы Tekla API.

Пока это отдельный архитектурный вариант для проверки производительности, а не обязательная часть текущего решения.
