# Roadmap: управление TeklaBridge из системного трея

## Цель

Добавить доступный из области уведомлений Windows интерфейс, который показывает
состояние svMCP/Tekla и позволяет управлять жизненным циклом `TeklaBridge` без
консольного окна:

- проверить состояние моста и последнее известное состояние соединения с Tekla;
- запустить или возобновить мост;
- остановить мост так, чтобы следующий MCP-вызов не запустил его незаметно снова;
- перезапустить мост;
- открыть журнал;
- по желанию включить запуск управляющего приложения при входе в Windows.

## Текущее устройство и причина отдельного управляющего процесса

Сейчас MCP-сервер (`net8.0-windows`) сам создаёт `PersistentBridge`, запускает
`TeklaBridge.exe --loop`, держит его stdin/stdout и передаёт ему JSON-запросы.
При ошибке транспорта bridge завершается и запускается заново при следующем
инструментальном вызове. Поэтому tray-приложение, которое только завершает
`TeklaBridge.exe`, не сможет обеспечить постоянное состояние «остановлен».

`TeklaBridge` (`net48`) должен остаться headless-консольным процессом: его stdout
является частью JSON-протокола MCP. Значок и меню Windows размещаются в отдельном
`net8.0-windows` WPF-приложении; tray icon предоставляет готовая библиотека
`Hardcodet.NotifyIcon.Wpf`.

## Целевая архитектура

```text
MCP client --stdio--> TeklaMcpServer --named pipe--> Tray/Bridge Controller
                                                       |
                                                       +-- stdin/stdout JSON --> TeklaBridge --Tekla Open API--> Tekla
                                                       ^
                                                       |
                                                 NotifyIcon UI
```

Управляющее приложение становится единственным владельцем дочернего процесса
TeklaBridge. MCP-сервер сохраняет текущий внешний MCP-контракт, но вместо прямого
управления дочерним процессом отправляет команды управляющему приложению через
локальный named pipe.

Если управляющее приложение отсутствует, первый MCP-вызов запускает его из папки
`controller` рядом с MCP-сервером. Опциональный автозапуск при входе в Windows
независим от этого механизма. Сохранённое пользователем состояние `Paused` не
сбрасывается автоматически: после `Stop Bridge` требуется явный `Start / Resume`.

## Принципы

- Не реализовывать системный tray API самостоятельно: использовать WPF и готовую
  поддерживаемую библиотеку `Hardcodet.NotifyIcon.Wpf` для tray icon/menu.
- Для IPC и владения процессом использовать штатные Windows/.NET API, без отдельного
  стороннего IPC/process-supervision framework.
- Сохранять текущие архитектурные слои и переносить существующий код управления
  процессом, а не переписывать bridge lifecycle заново.
- Не добавлять UI в `TeklaBridge.exe` и не писать посторонние данные в его stdout.
- Не завершать дочерний процесс напрямую из tray-клиента; команды Stop/Restart
  обрабатывает единственный владелец процесса.
- Named pipe ограничить текущим Windows-пользователем (`PipeOptions.CurrentUserOnly`)
  либо эквивалентной строгой ACL.
- Передавать существующий `BridgeRequest`/`BridgeResponse` без изменения их
  контракта; для tray-действий использовать только небольшой фиксированный набор
  control-команд, без универсального IPC-фреймворка.
- Сериализовать все обращения к одному экземпляру TeklaBridge, как это делает
  текущий `PersistentBridge`; MCP-клиенты в разных процессах занимают общий
  пользовательский mutex на время запроса, чтобы запросы не сталкивались в pipe.
- При завершении TeklaBridge дождаться выхода процесса до освобождения файлов и
  запуска следующего экземпляра; сообщать об ошибке, если процесс не завершился.
- Не опрашивать Tekla часто в фоне: показывать последнее известное состояние и
  обновлять его по событиям/ответам управляющего процесса или по явному запросу.
- Автозапуск сделать необязательной пользовательской настройкой.
- Не делать Windows Service: компонент работает в интерактивной пользовательской
  сессии Tekla.

## Этапы

### Этап 0. Контракты и жизненный цикл

- Зафиксировать состояния: `Stopped`, `Starting`, `Running`, `Paused`, `Faulted`.
- Развести состояние процесса и состояние соединения с Tekla; последнее может
  быть неизвестным или устаревшим, если проверка давно не выполнялась.
- Определить поведение Start, Pause/Stop, Resume, Restart и Exit, включая
  одновременные запросы MCP и действия пользователя в трее.
- Сохранить поиск установленного `TeklaBridge.exe` для TS2025+ и fallback на
  `bridge` рядом с MCP-сервером; перенести/переиспользовать разрешение пути так,
  чтобы оно не расходилось между компонентами.
- Утвердить фрейминг, версию и таймауты named-pipe протокола, не меняя JSON-контракт
  команд TeklaBridge.

### Этап 1. Управляющий процесс

- Добавить отдельный WPF-проект `TeklaBridge.Controller` (`net8.0-windows`) с
  `Hardcodet.NotifyIcon.Wpf` и одним экземпляром на пользовательскую сессию.
- Использовать штатные `System.IO.Pipes`, `System.Diagnostics.Process` и
  `System.Threading.Mutex`; не добавлять других сторонних пакетов для IPC,
  процессов или интерфейса.
- Перенести/переиспользовать текущий `PersistentBridge` как владельца процесса,
  stdin/stdout/stderr, таймаутов и аварийного восстановления TeklaBridge.
- MCP-клиентский канал оставить простым локальным named pipe, ограниченным
  текущим пользователем. Не добавлять отдельную службу или сетевой транспорт.
- Реализовать только необходимые control-команды `Status`, `Stop`, `Resume`,
  `Restart`; `Execute` пересылает существующий запрос моста как есть.
- При Stop закреплять `Paused` в управляющем процессе и отклонять обычные
  `Execute`, пока пользователь не возобновит работу.
- Корректно завершать pipe-клиентов и дочерний bridge при штатном завершении
  управляющего процесса.

### Этап 2. Подключение MCP-сервера

- Заменить прямой вызов `PersistentBridge` на тонкий клиент named pipe,
  сохранив публичные MCP tools и существующие command timeouts.
- Сериализовать MCP-запросы из нескольких клиентов именованным mutex; ожидание
  очереди происходит до начала таймаута конкретной операции Tekla.
- Передавать через pipe только те Tekla-команды, которые уже формирует MCP facade.
- Не менять команды TeklaBridge, DTO ответа и публичные схемы MCP tools.
- При недоступном/старом контроллере возвращать короткую понятную ошибку с
  инструкцией запустить или обновить управляющее приложение.
- Проверить восстановление после потери pipe, падения TeklaBridge и повторного
  подключения без потери соответствия request/response.

### Этап 3. Tray UI

- Добавить tray icon из `Hardcodet.NotifyIcon.Wpf`, подсказку с кратким состоянием
  и стандартное WPF `ContextMenu`:
  состояние, Запустить/Возобновить, Остановить, Перезапустить, Открыть журнал,
  Автозапуск при входе, Выход.
- Блокировать невозможные действия и показывать понятный результат команды.
- Оставлять меню открытым после выбора команды или переключения автозапуска;
  клик вне меню закрывает его.
- Показывать раздельно состояние процесса моста и последнее известное соединение
  с Tekla; подпись должна говорить `last check`, а после Stop/Resume/Restart или
  ошибки транспорта соединение становится `not checked` до следующей проверки.
- Сделать обычное закрытие окна (если окно настроек будет добавлено) сворачиванием
  в трей; отдельный пункт меню завершает управляющий процесс.
- Для единственной пользовательской настройки автозапуска использовать штатный
  Windows Startup механизм; хранить только необходимый пользовательский флаг.
- Не требовать прав администратора.

### Этап 4. Деплой и проверка

- Сборка MCP-сервера копирует WPF-контроллер и его зависимости в
  `TeklaMcpServer/bin/<Configuration>/net8.0-windows/controller/`.
- Для Tekla Structures 2025 `TeklaBridge.exe`, `TeklaMcpServer.Api.dll` и
  `SolidContacts.Core.dll` после остановки моста копируются в
  `C:\TeklaStructures\2025.0\Environments\common\extensions\svMCP\`;
  инструкции находятся в родительском `README.md`.
- Не копировать .NET 8 controller и его зависимости в Tekla extensions.
- Сделать автозапуск включаемым и выключаемым пользователем; по умолчанию не
  включать его без явного выбора в установке/настройках.
- Проверить сценарии: Tekla закрыта/открыта, bridge аварийно завершился, Stop во
  время MCP-вызова, Restart после ошибки, несколько MCP-клиентов, контроллер
  отсутствует/обновляется, выход пользователя из Windows.
- Добавить минимальные contract-тесты для pipe-протокола и unit-тесты переходов
  состояний; провести ручную проверку меню и уведомлений в Windows.

## Вне объёма первой версии

- Удалённое управление по сети.
- Windows Service, повышенные права и управление другими пользовательскими
  сессиями.
- Произвольные Tekla-команды, shell-команды или список процессов в UI.
- SSE/HTTP транспорт для сторонних потребителей: это отдельное направление и не
  требуется для локального tray-контроля.

## Текущий статус

- Добавлен WPF tray-контроллер на `Hardcodet.NotifyIcon.Wpf` 2.0.1.
- MCP-сервер передаёт запросы контроллеру через локальный named pipe; контроллер
  использует текущий `PersistentBridge` для владения `TeklaBridge.exe`.
- При первом MCP-запросе контроллер запускается автоматически, если pipe недоступен.
- В меню есть `Start / Resume`, `Stop Bridge`, `Restart Bridge`, `Open log`,
  `Start with Windows` и `Exit`; интерфейс приложения — на английском.
- Меню остаётся открытым после выбора команды или переключения автозапуска и
  закрывается кликом вне меню.
- `Stop Bridge` сохраняет `Paused`. `Start / Resume` и `Restart Bridge`
  снимают паузу только после успешного старта моста.
- MCP-запросы сериализуются между процессами named mutex; Stop/Restart дожидаются
  завершения TeklaBridge до освобождения его файлов.
- Трей показывает `Tekla: last check connected/disconnected`; после изменения
  состояния моста или ошибки вместо устаревшего результата показывается
  `Tekla: not checked`. Фоновый опрос Tekla не выполняется.
- Успешно проверено вручную до последних исправлений: tray запускается и
  соединяется с моделью `PR2613.db1`. Последние исправления собраны; повторная
  ручная проверка Stop/Restart, параллельных MCP-вызовов и перезагрузки Windows
  остаётся в плане.

## Ограничение объёма

Контроллер — тонкий адаптер вокруг текущего процесса `PersistentBridge` и API
Windows/.NET. Он не должен превращаться в новый framework для приложений, очередь
задач общего назначения, сетевой daemon или отдельную бизнес-логику Tekla.
